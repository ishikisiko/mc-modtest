# 开发与检查流程

本文件是工作方式、检查升级和版本规则的唯一入口。用户当前要求优先；模块技术约束见 [contracts](contracts/README.md)，实现说明见 [知识库](ai-kb/INDEX.md)。旧报告中的全量清单只是那次执行记录，不是新任务的默认义务。

## 默认路径

明确改动 → 实施 → 必要检查 → 提交并报告实际结果。

普通工作不创建 proposal/design/tasks，不运行 OpenSpec，不启动 CRAFT run，不要求多角色审批或归档。复杂设计有真实歧义时才写一份简短说明；不为流程而造文件。用户明确选择 GenOps 时才启用其可选工具。

开始执行前明确三件事：改了什么、最小检查是什么、什么具体失败才需要扩大。可以用一句话说明，无需新表单。必要检查通过就收尾；提交或合并本身不触发全量发布验收。

## 最小检查

| 改动 | 默认检查 | 何时需要更多 |
|---|---|---|
| 不进入 jar 的文档、报告、流程说明 | 受影响链接/路径与 diff；纯文字不必测试 | 修改了可执行命令或机器读取规则时检查对应消费者 |
| Python 工具/调度器 | 被改行为的 focused tests、离线命令计划 | 改了真实启动、输入或清理边界，且离线检查无法证明时，选一个最短真实探针 |
| 游戏验收脚本 | 相关 parser/fixture/dispatch 测试 | 改动涉及实际交互时只跑受影响场景；不同时追加整套玩法验收 |
| Java 纯逻辑/数值或数据 | 相关单元测试、受影响 schema/资源检查；必要编译 | 事件、注册、网络或打包边界被改时增加对应集成探针 |
| UI/模型/贴图 | 受影响资源检查与代表性画面 | 布局通用规则或语言变化时扩展相应尺寸/语言，不默认六套全拍 |
| 存档、协议、共享状态 | 相关迁移/codec/授权测试 | 改到生命周期就做对应重启；改到多玩家权威才做双客户端 |
| 生成器/构建/依赖 | 修改的生成族、打包关系或消费者 | 共享输入影响多个模块时覆盖那些消费者；核心依赖迁移可触发更广验证 |

触及存档、协议和权威边界时，必要证据会更多；不能先故意漏测再等玩家出错。范围由影响决定，不由文件数量决定。

## 失败时如何扩大

1. 保留失败日志，先判断是产品、fixture、环境还是工具问题。环境启动失败不扩大玩法测试。
2. 有明确局部原因：修复后复验失败检查及直接邻接回归。
3. 原因未明或证据涉及共享模块：扩展到对应模块及消费者，并记录触发依据。
4. 只有明确跨模块风险或用户要求完整发布验收时，才运行全量 release。

每次扩大必须能回答“新增哪项检查、它能排除什么具体疑点”。不要把一次失败变成固定层层升级到全仓的阶梯。失败不是修改测试预期以消除红灯的理由。

## 重型运行和结果复用

- 必需的 Gradle、服务器、客户端或双客户端运行放在 Modal；没有自动本机重型回退。轻量 Python/文档检查留在本地。
- 固定提交与依赖身份；只复用与相关输入一致的证据。只改说明/测试准备时不重复未受影响的构建，但报告不同提交和差异。
- 同一短期固定源运行可以共用 Sandbox 和编译产物；不要为等待设计长期挂云环境。记录失败与终止确认。
- Chunky 仅用于相关结构/世界生成检查，不是普通玩法的必经前置。当前某个完整 preset 若仍内含 Chunky，不要为了局部检查选择它；本次流程清理不重写游戏采集器。
- 独立场景明确 selected/completed/unrun；局部通过不能称全量通过。软件渲染、命令准备与开发者截图不能代替玩家手感、性能或多人验收。
- 检查预算用于发现异常耗时，不能用超时预算当作通过条件。超过预期先定位，不机械重复整套流程。

## 版本和交付

当前是开发阶段：只支持当前开发版本，不维护旧存档、旧世界算法或历史资源兼容。只打包当前运行需要的资源；生成链的中间输入不因此成为必须随包保留的旧资源。不得默认追加旧版别名、迁移层、历史摘要基线或跨版本兼容验收。

版本仅随实际交付的 mod 内容、运行时行为、资源或打包兼容性变更而调整。纯测试工具、流程、非打包文档和注释修复不升级 mod、不构建 jar、不启动游戏。

确需发版时，版本规则保持：大功能 `0.x.y → 0.(x+1).0`，小功能递增 y，单一已验证修复使用 `-fix1/-fix2`。`python3 tools/bump_version.py <version> [--dry-run]` 同步 gradle.properties、mod metadata、README jar 示例和 CHANGELOG；仅在这类交付中要求它们与实际 jar 一致。

需要给玩家试用的新内容应提供匹配 jar 和使用说明，但无需因此重跑无关全仓检查。`tools/release_gate.py` 是明确选择的完整发布工具，不是每次任务的完成定义。

Git 默认从 main 开分支；完成后提交、fast-forward 合并 main 并推送，除非用户另有要求。不动无关未提交文件。

## 文档与汇报

- 通用技术约束在 docs/contracts/；模块解释在 docs/ai-kb/；使用命令在 README。各有职责，不再维护第二套 OpenSpec 规范。
- 只改受影响说明；新知识库条目进入 INDEX。数据已有事实不再复制为文档常量，历史结果标明版本和范围。
- 历史提案/任务/设计从 Git 检索；保留有用延期项和未确认验收，不能因清理文件就改成已完成。
- 最终用中文说明结果、实际检查、必要限制和提交。只有耗时重要时给测量分项；无法测量的实现/协调时间不叫“模型思考时间”。
