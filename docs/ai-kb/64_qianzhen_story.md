## 数据与写入所有权

- `blueprints/qianzhen/` 原六份蓝图与 `manifest.json` 拥有建筑和相对位置；
  `story_scene.json` 拥有道路、剧情站位、调查目标及独立的三项教学/工作设施。
- `tools/qianzhen/story_assets.py` 生成 `build/generated/qianzhen/resources`，
  由 `generateQianzhenStoryAssets` 纳入 jar。不要手改结构 NBT 或派生位置表。
  无 seed 调用始终使用 authored 默认，不隐式启用离线地点生成器。
- `data/myvillage/story/qianzhen_actors.json` 定义人物身份与角色。
- `data/myvillage/story/qianzhen_chapter_1.json` 保留 version1；
  `qianzhen_opening.json` 拥有 version2 的中文流程、工作和报酬配置。
  定义在服务器启动时加载并校验，不承诺在线热重载。
- `data/myvillage/story/qianzhen_entrance.json` 拥有首次入口的有界规划预算和提示；
  既有场景使用保存的冻结几何，三个精确历史版本另有只读归档。
- 个人任务使用独立 Attachment，死亡复制由 `copyOnDeath` 负责。任务服务
  是写入口；客户端只接收快照、提交当前对话的有界选项。
- 人物由 WorldSim 保存，WorldSimAvatars 管理唯一、非持久身体。角色不是
  另存一份的实体，也不因重进或靠近而再次生成身份。

人物采用明确的剧情保护规则，避免后台突破、寿元或普通伤害使章节永久
中断；这只适用于已绑定的剧情角色。周禾是炼气初入的年轻采药人，没有
为本章新增命簿凡人境界或专属实体类型。

## 修改剧情内容

章节 JSON 中 `stages` 定义当前目标、对白与后续阶段，`actions` 定义
角色交谈、精确地点调查和交付动作。version2 另有服务器专用 `fact` 边，
不出现在对话选项，也不接受客户端提交；真实培养事实与个人播种收据负责推进。
接受、领苗、领奖仍须本人真实 NPC 会话授权。`requires` 引用已取得的证据 ID，
`next` 指向稳定阶段 ID；对白和追踪变体按顺序匹配已有证据、共享返回与
古阵处置事实。条件是有界事实表，不执行任意命令或脚本。

改文字时保留稳定 ID。改变流程并增加 `version` 后，新玩家会在正式接受
时绑定新版本；已接取的旧版本进度不会自动清空或重绑，须另做明确迁移。
重复 ID、悬空引用、非法条件、不可达结局和自动循环会拒绝加载整份定义。

## 共享事实与个人任务

version2 是共享世界中的个人自愿进度：玩家各自选择何时参与和继续，无同队
同步或倒计时。多人重点是家园、聚落建设与刷怪；未接或暂离剧情不锁自由玩法。
version1 的共享事实保持原语义：救援后周禾使用同一命簿身份回到药庐；这是
剧情安排送回，不是实机步行护送机制。古阵限额恢复同样是场景共享事实。后来接任务的玩家可在当前
位置访问人物、核实已发生的结果，再推进自己的任务和领取自己的报酬。
另一玩家完成操作不会直接写入本人的完成或奖励记录。

调查必须真正右键定义中的方块，服务器核对场景、维度、距离、视线、
方块状态与当前步骤。对话会话绑定当前身体、人物租约和个人进度版本；
过期或重放选择不能推进。奖励先检查背包容量，正常保存后的重复交付不
再次发放；满包时保持待领奖。

## 进入与界面

普通主世界首次创建时，入口模块观察真实首次出生事件，在最终出生点确定后
做有界候选规划与整地，部署独立阡镇并铺设实体步道、护栏和照明。保留原出生点
及 V4 冻结 plan；候选需通过自然方块、实体、区域、城市/山门和查询/写入预算
检查。**不保证任意种子成功**：无合适候选记录 UNAVAILABLE；写入失败记录 FAILED，
重启不自动重放。默认不自动初始化超平坦世界，道路不提供无敌或伤害豁免。

靠近只给简短聊天线索；本人右键读招募木牌后，主动记下方向，再自行入镇
找程砚或沈岚。读木牌、追踪、接近或看见 NPC 都不自动接受任务。

当前已注册入口：

```mcfunction
/qianzhen where
/qianzhen recruitment
/qianzhen recruitment track
/qianzhen recruitment stop
/myvillage qianzhen entrance status
/myvillage qianzhen entrance bind_notice <x> <y> <z>
/myvillage qianzhen deploy <x> <y> <z>

```

`recruitment` 与 `track` 须本人已读有效木牌；`stop` 停止招募追踪，不撤销已接受
的个人章节。`myvillage` 管理入口要求权限等级2。`bind_notice` 只为已有 COMPLETE
场景绑定一块已放好的主世界木牌，受距离和入口状态限制；只更新该木牌文字和
收据，不铺路、不补建筑。`deploy` 保留管理员在独立平坦预览世界的显式部署用法，
重复部署不能覆盖既有场景，不能拿它给用户原存档重放模板。

旧世界不自动整地或补设施；已有场景读取实际保存几何/历史布局，新学徒接受还
要求元数据与真实两碑、灵土通过核验。缺设施或区块未加载可能使新路线不可用，
原 version1 不受新设施 gate 影响。换 jar 不会使原存档屋顶或药圃自动更新。

任务追踪保留右上纯文字，默认 `O` 打开行迹、`Y` 切换追踪显示，可重绑定；
`P` 保留原版社交菜单。新增单一当前目标标记，透遮挡、屏外方向和距离；
人物优先定位当前加载的命簿身体，未加载时用服务器权威位置，不追旧救援点。
未接受且未主动追踪、无目标、未知位置、跨维度、完成或隐藏状态不显示标记。
网络协议为 **45**，原生视觉和玩家可读性仍 `not_verified`。

输出 `resources/data/myvillage/structure/qianzhen/*.nbt` 和
`resources/data/myvillage/story/qianzhen_scene.json`，沿用现有 Java 部署 schema

源变更会更新默认资源身份。
离线 seed 不进入运行时，不重抽已部署场景、不改变人物身份/章节定义、不自动

原生采集器默认仍读取 authored 来源；seeded 必须显式使用 `--candidate` 和
固定请求，不能把 authored preset 结果记为生成候选通过。候选资源启动前安装、

## 2026-10-24 玩家验收反馈：第一章体验（仅记录，未实施）

以下来自玩家在 DevHost 主 seed `20261024` 场景中实际游玩后的反馈。
此处只保存问题和初步设计判断，不代表已经修改建筑、剧情、界面或物品。

1. **建筑屋顶与结构。** 一些房顶和结构设计不好。此次没有指定具体地点；
   后续玩家要求整改时，先询问并请其提供对应位置的截图，不提前推断为全部建筑重做。
2. **剧情目的与玩法。** 剧情有些不知所云，目的性及与玩法的关联不强，像跑腿，
   有些繁琐并且无趣。
3. **非战斗目标追踪。** 希望当前目标上方有小型悬浮、可穿透遮挡看见且足够明显的
   光景或标记，特别是非战斗目标，以便找到人物和调查位置。
4. **专用调查物品。** 运药账等需要调查的关键物件可以做成专用物品，而不是只用
   原版方块表达；直接使用原版内容在体验上有些无趣。

### 初步设计判断（待后续讨论，不是已定方案）

- 这四点应作为一次“调查体验重构”来思考，而不是分别补几句对白、加一个图标、
  换几件贴图。当前主要问题是行动没有形成“目的 → 发现 → 判断 → 处置 → 世界反馈”
  的闭环；如果九个调查点只是解锁下一段跑腿，增加文本不能解决无趣。
- 后续重排时先明确本章的问题和玩家作用，再减少重复调查与往返。每个保留步骤
  至少应带来新信息、实际选择、能力或状态变化、可见后果之一；终局需要让玩家直接
  看到灯、药田或人物处境因自己的行动而改变。具体保留或合并哪些调查点尚未决定。
- 目标追踪用于降低无效寻路，不应替玩家完成调查。可只显示当前主目标，近处切换为
  精确交互位置，阶段变化时同步更新；透视、距离与视觉强度需实机调整，避免满屏标记。
- 专用物品应服务于证据阅读和判断。例如运药账可以成为能打开核对货数与时辰的账册；
  其他物件按剧情必要性选择，不应把所有目标改成拾取或交付任务，也不能只换外观而
  保留原来的跑腿链。
- 建筑暂不作通用整改结论。待玩家指出并截图后，再按屋顶轮廓、比例、结构逻辑、
  入口和行走视线逐项判断。


## 本轮已确认方向与实现状态（0.87.0 准备中）

本节记录反馈后的已确认方向，取代上方“初步设计判断”作为本轮实施依据；
原反馈和讨论全文保留，不将专用调查物品或重写旧调查链当作既定交付。

- **开局与互惠。** 普通空手生存，自主发现招募，入镇向沈岚询问短工并看清约定。
  先通过既有测灵/天命/传承服务和真实吐纳结算学习，再领一份种苗、本人补种三个
  不同格，最后领取一次有限报酬。真实教学事实和第三格播种自动衔接；玩家对话
  推进仅接受、领苗、领奖（`accept`、`take_supplies`、`claim_reward`）。旧四个
  confirm/report ID 是 server-only fact，不能作为玩家点击或发包路径。
- **既有修行。** 接受时只读已有灵根、天命、基础吐纳与真实修行经历，不重抽或
  改写境界、主修和熟练度；稳定度本身不构成免做首次吐纳的依据。未接受不自动
  推进，也不发种苗或报酬；教学可按个人时间在家完成，再回沈岚领苗/领薪。
- **公共药圃。** 本人三个不同格的真实生存播种才计数，他人、同格重复、取消或
  被后续合法替换的原播种不计。后到者可真实收获成熟灵叶再补种，未成熟必须等，
  不清空他人苗、不伪造生长。种苗只发一次，遗失需自行取得灵叶或收成熟灵叶。
  公共药圃没有有限等待或反恶意占地保证：卸载不长、占格抢收、破坏灵土均可能
  长期阻塞可选工作；自备种苗不能解决占格，自由建造/修炼/战斗仍不受限制。
- **多人和后续方向。** 多人侧重家园聚落建设和刷怪，主世界个人章节各自择时，
  无时限、无队伍同步。隐世高人、早期小物件金手指、重要剧情个人秘境只是后续
  方向讨论，尚未实现，也未冻结详细剧情；当前没有神物、洞天或特殊住宿安排。
- **屋架与设施。** 截图已定位渠圃清水釜取样亭，生成源补柱梁支承并检查同类桥廊，
  保持原瓦面逐格不变；药庐增加初始净空灵土，场景独立登记两碑与药圃设施。
  屋架/药圃32项、最终整合 assets12项/contract11项/SceneLayout6项/pipeline5项均有
  离线证据，不能写成原生放置、视觉或交互完成。换 jar 不会自动修复既有屋顶；
  需要重生成到独立预览世界，或使用明确有界的旧档修复方案，禁止模板自动重放。
  独立旧档修复入口的精确版本、原状态检查与原生待验范围见下节。
- **旧布局兼容。** 新部署冻结完整实际几何；旧布局仅精确支持有来源的
  `1-93b7ddbc5c59392e`、`1-f795e60913419e05`、`1-56da335c3dd1262f`，保存版本与
  坐标不改。未知历史版本拒绝，保留存档并使用匹配 jar；不是全旧档兼容承诺。
  缺新设施的旧世界不自动补建、不覆盖地物，新学徒可能不可用；原旧章保留。
- **当前证据。** story-polish-r2 直接 javac/JUnit 51项与 Python合同4项通过，
  marker 数学4项和静态设计预览通过；仅证明对应纯逻辑/离线范围。完整编译、
  protocol45 codec、自然首次入口、真实教学/播种/领奖、旧章重启、旧档修复、

```mcfunction
/myvillage qianzhen repair_roof preview

```

块态和原因；`apply` 重新全量核验，只将目标空气补为支架。再次执行已修场景
