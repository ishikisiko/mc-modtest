## 绑定已有建筑

命令只登记命簿场所，检查站位和指定设施，不放置、覆盖或修复方块，也不强制加载区块。先由玩家正常进入建筑，把入口、楼梯、客房、药铺和测试路线加载出来。`bind` 成功只代表登记成功；`status site` 的每个点仍须检查为 `available`。

### A. 大陆规划中已有的云山占位城

```mcfunction
/myvillage worldplan info
/myvillage life yunshan
/myvillage life status site yunshan
```

读取 `WORLDPLAN` 输出中的 `city.x`、`city.baseY`、`city.z`，确认自己在这座城市。该命令使用实际规划锚点和冻结布局哈希；首个城市原点区块正常可用后也会自动登记地点，自动登记不招募人物。

显式绑定同一已有布局的形式如下，三个坐标须替换成 `WORLDPLAN` 返回值：

```mcfunction
/myvillage life bind yunshan yunshan_planned_v1 <city.x> <city.baseY> <city.z>
```

`yunshan_planned_v1` 对应当前冻结城市里的客栈 V3、药铺 V1。大陆 V2 是地形/生态算法版本，仍可能装载这套旧城市布局；不能据“大陆 V2”改用下面的放大样板布局。布局哈希不符时保留失败，不把场所强行套在另一套建筑上。

计划城有 11 个场所。两个住客使用客栈的两个真实客房床位；掌柜在后场休息站休息，药师有药铺真实床位。掌柜的休息站不是新增床铺。

### B. 云山四栋放大样板世界

若使用 [放大样板世界](2026-10-17-yunshan-expanded-buildings.md)，且四栋保持原位置、朝向，布局最小角是 `(0,-61,0)`：

/myvillage life bind showcase yunshan_showcase_v2 0 -61 0

这套布局有 13 个点，其中客栈有四个互不重复的客房床位。`bind` 不把样板建筑安装进大陆城，也不缩放或旋转建筑。若人为移动了整套样板，提供整体移动后的最小角；若分别移动或旋转了建筑，先使用适配的 authored 布局，不能猜一个新原点混用。

同 ID、同布局、同原点重复绑定应保持原注册数据，已经手工添加的采集点也保留；同 ID 改成不同原点或布局应明确拒绝。可在登记前后记录城市已有审计或方块读回，确认登记过程没有改变建筑。

## 手动采集点与 4 人演示

首期没有从蓝图推定“灵田”。找一个从客栈和药铺能步行到达、在同一命簿地区内的现有空地点：脚下有完整落脚面、脚部和头部有净空。站稳后执行对应一组命令：

```mcfunction
/myvillage life place yunshan gather_lane gather ~ ~ ~
/myvillage life demo yunshan
/myvillage life status site yunshan
```

或在放大样板中：

```mcfunction
/myvillage life place showcase gather_lane gather ~ ~ ~
/myvillage life demo showcase
/myvillage life status site showcase
```

`gather_lane` 是管理员显式声明的有限额度抽象采集点。它记账，不收割方块、调用灵植掉落或向玩家背包发物品。保留实际采集额度与现场截图，验证现场植物/地面没有被修改。

`demo` 只按 ID 选取该地区中已存活、无宗门、`rank=rogue`、不在旅行或闭关、尚未分配生活的真实命簿人物。它不增加人口、不复制身份、不从别的地区拉人。四个分工为：

| 角色 | 住处 | 指定岗位 | 主要验证 |
|---|---|---|---|
| `innkeeper` 掌柜 | `inn_rest` | `inn_work` | 服务、领取工资、休息 |
| `herbalist` 药师 | `herbalist_rest` | `herbalist_work` | 有药材才配药、消耗库存、产出药品记账 |
| `rogue` 散修 | `guest_west` | `gather_lane` | 采集、交售、赚取盘缠、修炼和休息 |
| `visitor` 客人 | `guest_east` | `herb_market` | 居住、日常交往与按需谋生 |

先检查全部缺失角色所需的站位和人数，再分配。人数不足、床位已满或设施不可用时应明确报告原因。人数不足属于演示前提未满足；记录需要人数与实际可用人数，可先用现有人物做部分案例，其余记 `unrun`，不要重置命簿或复制四个身份凑结果。`world here` 和 H 面板天下页可检查本地人物，`world person` 可读候选的身份/状态。

手工分配、解除与改绑的形式为：

```mcfunction
/myvillage life assign <人物ID> yunshan rogue guest_west gather_lane
/myvillage life status <人物ID>
/myvillage life unassign <人物ID>
```

相同分配不重置活动，重复 `demo` 不重复招人。已分配人物要改绑时先 `unassign`；这只解除生活职责，不删除命簿人物。复现任务中不要通过反复解除/重绑观察正常日常续存，因为重绑本身建立新的生活记录。

## 如何读状态、账目和路线

每个关键步骤前后执行 `life status <人物ID>` 和 `life status site <siteID>`，保留完整聊天/服务端输出。人物命令包含可解析的 `NPC_LIFE { ... }` JSON；场所命令列出场所可用性及库存摘要。

| 字段 | 读取目的与判据 |
|---|---|
| `personId/siteId/homeId/workId/role` | 确认同一命簿身份与固定分工 |
| `phase/activity/targetId/reason` | 区分等待、移动、执行；目标和改计划原因应与现场相符 |
| `revision` | 标识一段活动；到达从移动转执行时仍属于该活动，不应靠重新生成实体获得第二份结算 |
| `epoch` | 标识本次实体执行权；撤回/重启后重新具现可变，旧实体不能完成新执行权的活动 |
| `embodied/observed` | 已有受管理实体/附近有符合条件的玩家；`observed=true, embodied=false` 时必须等待，不暗中工作 |
| `x/y/z` | 最近权威脚底位置；实体沿路移动，不跳到屋顶、异地宗门或旧随机点 |
| `progressTicks/requiredTicks/completedActivities` | 到达之前不能积累工作时长；完成次数与账目变化对应，停顿/重启不能重复结算 |
| `pauseTicks` | 交谈时的短暂停顿；不是永久卡死 |
| `herbs/coins/fatigue` | 人物药材、盘缠和疲劳，按实际完成活动改变 |
| site 的 `stock/medicine/treasury/gatheredToday/services` | 药铺库存、药品、场所资金、当天采集量、已完成服务数；采集量有限，付费/工资不凭空同时增加双方的钱 |

常规闭环应观察到：散修走到采集点并完成采集后增加药材；在市场完成交售后药材转入场所库存、场所资金转给人物；药师完成有效配药后消耗库存并增加药品；服务/工作有时长；疲劳或日程触发住处休息。修炼只结算真正获得的生活修炼时长。以上是首期内部资源账，不是玩家交易界面、实体容器物流或炼丹炉自动配方生产。

路线代表点可用 `status site` 读出绝对坐标。计划城 `guest_west` 相对锚点 `(34,6,82)` 到 `herb_market` `(46,3,60)` 跨越客栈楼梯和街区；放大样板 `guest_west` `(52,7,55)` 到 `herb_market` `(4,1,6)` 约 69 格，适合检查分段路径、楼梯和跨院移动。这里只给蓝图相对坐标，NPC 实际目标仍按运行时输出判断。

## 真人案例与通过条件

以下为各项验收判据，分别记录 `selected/completed/unrun`。后续 Modal 结果见上方验证记录；自动化覆盖的范围与玩家亲自验收分开判定。

| 案例 | 操作 | 必须观察到的结果 |
|---|---|---|
| `bind_idempotence` | 正常进入建筑，绑定两次；已加采集点后再绑定 | 场所数量不重复，采集点保留，楼房方块不变，未新增人物 |
| `demo_identity` | 记录人口和 4 个 ID，执行 demo 两次 | 第一次分配已有 4 人；第二次无额外分配；同一 ID 只有一个生活记录 |
| `day_loop` | 保持玩家近处，跟随散修完成采集→交售，观察药师/掌柜/住客 | 真实走到目标才开始执行；时长和库存/资金变化对应；有可见休息/交往/修炼选择 |
| `conversation` | 靠近同一 NPC，用实际右键交谈；等短暂停顿后再谈 | NPC 转向、停步，文本说明当前活动/原因，之后继续；同一模拟日反复交谈不反复刷熟识 |
| `blocked_route` | 在隔离副本记录原方块后，临时堵住正在使用的门/走廊，保持目标站位本身完整 | 不能穿墙或瞬移；出现 `stuck/path_unavailable/path_timeout` 等实际原因，放弃/重试或改计划；被堵活动不结算。恢复原方块后能重新寻路 |
| `removed_facility` | 按 manifest 的真实 `block_pos` 记录并临时移走药铺炼丹炉或住客床，再读 site 状态 | 对应点变 `blocked`，该点活动停止/重规划，不继续用已不存在设施生产。恢复同种方块后重新观测可用并恢复行为 |
| `unload_return` | 先完整观察可用设施和成功路线，所有玩家离开超过撤回距离；保留一名在线玩家在远处，再回来 | 化身撤回而命簿 ID 保留；远处允许依据有效观测作有限抽象推进，不强载城镇；回来读取同一库存/活动，不重领完成奖励或重复实体。已报告失败的路线不能一离远就被当作成功 |
| `restart_mid_activity` | 在 `moving` 或未完成的 `working` 阶段读 JSON，正常保存停服；保持停服一段墙钟时间后重启同一副本 | 人物/站点/账目保留；停服时间没有额外生产；工作已获得进度保留，移动可从保存位置重算剩余行程；重新具现更新执行权，同一活动不重复结算 |
| `two_players` | 两个真人客户端同时靠近同一居民并分别交谈；A 离开/B 留下，再全部离开 | 两人看到同一实体/同一命簿 ID；两人的认识记录各自维护；A 离开不撤回 B 仍在观察的实体；总产出不因两位观察者翻倍 |
| `avatar_cap` | 在独立副本正常停服，把 `[avatars].max_avatars` 临时设为 1，重启后靠近 4 位居民；随后恢复原值并重启 | 总化身遵守全局上限；近处未获名额的人 `observed=true, embodied=false`，进度/收益不变；获得名额后按当前计划继续，不补发等名额期间收益 |
| `occupied_spawn` | 人物远处撤回后，在其已记录脚底位置临时放置障碍，再靠近 | 身体不能挤进方块；附近但无安全身体时不暗中工作，恢复站位后正常具现 |
| `unsafe_checkpoint` | 在隔离世界用管理员命令将已具现身体悬空一格，撤回后再回来 | 保留实际经过的安全检查点和资产，以新租约恢复唯一身体；这是受控投影回归，不是自然跳跃或映射输入证据 |
| `sect_regression` | 去已有正常宗门，检查守山执事、符合资格的入宗/离宗、事务、长老交流和 H 天下页；再回城镇 | 旧功能仍可用；生活居民不被选成异地守山执事/随机化身，不因后台招募、立派、叛门或战斗瞬移/死亡 |

堵门和拆设施只在测试副本中进行，记录原方块完整状态并恢复。路上玩家暂时占位不等于永久设施损坏。床位检查定位的是真实床方块，NPC 的脚底休息站在床旁；本版未声称已经实现躺床动画。

双玩家重复检查可对指定人物做只读实体查询，下面 `42` 换为实际人物 ID：

```mcfunction
/execute as @e[type=myvillage:cultivator,nbt={WorldSimPerson:42}] run data get entity @s UUID
```

两位玩家近处应对应同一个受管理实体。重启后实体 UUID 允许变化，命簿人物 ID 必须保持；以 `epoch` 和账目判定接管是否正确。服务器日志的 `NPC_LIFE_AVATAR action=spawn/state` 可与 JSON 对照。不能通过单次名字截图证明没有重复实体。

冷区使用最后一次有效设施观测和有限行程估算，不会加载区块来实时检查尚未见到的损坏。测试应分别记录“亲眼观察后已知损坏”和“离开后未加载区块中的未知变化”，不能把后者报告成已经实时验证。

## 世界日历与 `/time` 的区别

生活日程和每日采集额度使用保存的修炼世界日历；只要有玩家在线，日历每个有效服务器 tick 推进一次。默认 `ticks_per_day=24000`、`days_per_year=24`，20 TPS 时一天约 20 分钟。无人在线、停服墙钟时间、睡觉跳夜、`/time set`、`/time add` 和 `doDaylightCycle` 都不会把这个日历直接跳到指定时段。

因此 `/time set night` 只能作为画面准备，不能证明生活居民的夜间休息逻辑已触发。使用 H 面板世界历和 `/myvillage world info` 对照，等待真实有效时间。`/myvillage world advance <days>` 是命簿宏观结算命令，也不是把 NPC 的移动/工作执行了同等天数；它适合独立宏观回归，不能拿来加速证明实体生活闭环。

需要缩短日程观察时，可在全新隔离测试世界建立前设置 `cultivation_time.ticks_per_day=6000`，并把这个前提写入结果，完成后恢复测试配置。修改时间尺度会重新解释已保存的原始 tick，因此不应在用于存档连续性对比的同一世界中途改变它。`world pause` 会暂停生活与宏观结算；`resume` 后不补发暂停期间的生活收益。

## 失败与交付记录格式

每个案例至少保留：场景 ID、时间、完整提交/jar 哈希、世界副本标识与种子、世界/模拟日、站点/人物 ID、两次完整 `NPC_LIFE` JSON、site 状态与账目、玩家坐标/模式、实际按键或鼠标操作、服务端相关日志和截图/短录像。记录结果 `pass/fail/blocked/not_verified`；未满足人数/布局/设施前提的案例写 `blocked`，未运行的写 `unrun`。

问题描述按“准备条件 → 实际操作 → 预期变化 → 实际读回 → 日志/图像路径”填写。复验前保留失败原始记录，说明修复了产品、fixture 还是环境。成功启动、命令返回成功、纯单元测试或开发者截图只证明各自覆盖的部分。

收尾时解除仅为测试添加的人物分配，恢复测试配置与临时方块，正常保存停服。记录使用的 4 个身份在命簿中仍存在；未把一般村民、城镇全部建筑或玩家本体迁成自动 NPC。最终交付报告分别填写构建、单人路线、设施损坏、存档/重启、双玩家、上限与旧宗门回归结果。
