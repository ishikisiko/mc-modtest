# 0.70.2 淬火水槽交付证据

## 范围

新增可合成、可注水的实体水槽，放在锻台同层正交邻格；淬火从该槽耗水，
器坯在槽内下沉、变冷并提起，伴随蒸汽与淬火声。水桶注水时返空桶，
空桶可取回未使用的水。真实器坯仍由锻台菜单持有，水槽只广播短期表现；
关闭中断保留水、返还器坯，完成时再次核对原槽存在、归属和水量。
所有新增文本与画面只做中文。

检查范围为资源、物品闭合、工坊相关 Java 测试，原生水桶／菜单操作、
保存重启、工序中断、拆槽和双人取水互斥。重型构建和游戏只在 Modal，
没有启动用户本机 Minecraft，也没有替换已有存档。

第一轮使用 `execute if block … run say TROUGH_FILLED` 检测水量，
但 `say` 只广播聊天消息，没有 RCON 返回内容。客户端和服务器日志都记录了
`TROUGH_FILLED`，同时背包已得到空桶，证明实际注水已发生；
采集器错误地把空回复判作空槽。已改为条件成立后执行只读 `data get block`，
不改变产品或测试预期。失败日志和原断言完整保留。

从 `bb106562` 到 `948c6c2a` 只修改采集器和非打包文档，Java、资源、
配置、构建定义及测试源码均未改变。因此复验使用 `workshop-play`，
复用先前通过的 41 项 Java 测试，只重新运行必要的原生场景。

第二轮定位到真实运行时问题：`ContainerLevelAccess.evaluate` 内部使用
`Optional.of` 包装回调结果，查找不到可用水槽时返回 `null` 会导致服务器异常。
已将回调改为始终返回 `Optional<QuenchingTroughBlockEntity>`，缺槽、空槽、
占用中均返回空 Optional；在接口外才转换成查找结果。
第三轮因此重新执行相关 Java 测试和原生场景，重点复验上述拒绝分支和拆槽取消。

本地 5 项工坊资源测试、23 项物品校验器测试、资源生成器 `--check`、
物品关系校验、受影响 Python 语法与 diff 检查均通过。
